# Personal GAS Contract v1

Independent Apps Script project, bound by ID to `1WU3UF1gTgut-Yx2dUn51Kk1fu2EHtnQSfxOOdx15-Y0`. Do not deploy together with the gerencia project. No production writes have been performed by this implementation.

## Transport and Identity

All GAS calls use POST JSON `{secret, action, payload, user:{username,name,role:"personal"}}`. The trusted Node proxy authenticates the person, supplies identity and secret, and strips the `personal-` action prefix: Node action `personal-bootstrap` forwards GAS action `bootstrap`, and `personal-upload` forwards `upload`. Logical GET actions are still POST to GAS. `doGet` always returns unauthorized. Never expose the secret in frontend code. Owner must set `GAS_API_SECRET` to a random secret of at least 32 characters in Script Properties. This is a single personal-finance namespace partitioned by trusted `username`; references must belong to that identity. Every JSON response has fixed namespace metadata: `{service:"personal-finance",spreadsheetId:"1WU3UF1gTgut-Yx2dUn51Kk1fu2EHtnQSfxOOdx15-Y0",success:true,data}` or `{service:"personal-finance",spreadsheetId:"1WU3UF1gTgut-Yx2dUn51Kk1fu2EHtnQSfxOOdx15-Y0",success:false,status,message}` (GAS transport remains HTTP 200; proxy must interpret status). These extra envelope fields are also present on unauthenticated GET, malformed requests and all failures, without exposing financial data. Failure `message` is always a nonempty user-facing Spanish string; there is no response `error` field. English internal diagnostics and unknown exception details are never echoed in these messages; unmapped diagnostics receive a Spanish fallback. The stored journal column and pending-operation property remain uppercase `ERROR`, with pending-operation text translated to Spanish in bootstrap. Authenticated raw backups retain original internal diagnostics. Actions, payload fields and financial enum values are unchanged; clients should branch on status/state, not translated message text.

The proxy must verify both exact namespace fields before forwarding any upstream data, even when a configured personal URL differs from the gerencia URL: a different deployment URL alone does not establish the service/document identity. Missing or mismatched metadata must be rejected, not treated as a legacy personal backend. Metadata is applied only at the pJson transport boundary, after supplied response values so it cannot be overridden. It is not part of financial rows, stored operation RESULTADO, idempotency input hashes or manifests. This unshipped source has no compatibility aliases. These markers guard deployment misconfiguration; they do not replace the shared secret or trusted user authentication.

Every mutation includes top-level **payload** `requestId` (UUID). Reuse identical action, payload and username for safe retries; a different input/user yields 409. PREPARADA or PENDIENTE_CONCILIACION reserves its request ID and cannot be replayed. While an owned operation is pending, all fresh mutations except resolveOperation are blocked. Resolve by explicit discard, inspect actual Sheets rows if needed, then submit a fresh UUID. Every edit includes `row.ID` and `row.UPDATED_AT` from bootstrap; stale versions yield 409. Ledger changes also touch the affected account versions, invalidating stale reconciliation tokens. All reads and writes use ScriptLock.

## Actions and Payloads

Unknown keys are rejected. Optional means omitted, not null. Financial amounts are JSON finite numbers, at most 1e9, with at most two decimals. Positive transaction/payment amounts; nonnegative catalog amounts. Dates are real `yyyy-mm-dd` Gregorian calendar dates (1900..9999), independent of timezone parsing. Descriptions/reasons must be nonempty. No PAN/CVV fields exist.

Executed-money temporal rule: `transaction.FECHA` (all income/egress/transfer/cardpurchase/cardpayment types), `pay.FECHA` and `reconcile.FECHA` must be <=configuracion.HOY, where HOY is today's date in the actual spreadsheet timezone. Valid date-only strings are compared without timestamp/timezone conversion. Same-day and past actual dates are allowed; future actual dates return Spanish status 400 explaining that future commitments belong in pending Cuotas. Rejection occurs before any journal, audit, payment allocation, account version or ledger write. Confirmed ledger rows are executed money, never a future scheduled-money queue: balances and paid states continue to use all active confirmed rows, and no automatic posting on a future day is introduced. These are new-write guards for this unshipped source, not a reinterpretation of hypothetical older future-dated ledger rows.

Future planning remains supported unchanged: Cuotas.FECHA_VENCIMIENTO, definition INICIO/FIN, card PRIMER_VENCIMIENTO and concrete card FECHA_CORTE/FECHA_MAXIMA_PAGO may be future dates subject to their existing calendar/order validations. Future pending commitments and recurrence generation do not move money. An actual payment today may pay a future-due commitment early, because the payment itself already happened; the supplied payment FECHA still cannot be in the future. Card installments may be scheduled in the future only for a purchase executed today or earlier. Reconciliation remains an audited adjustment to current computed balance, including when recorded with a past date; it is not a reconstruction of historical bank balance.

`transaction.type`: `income`, `egress`, `transfer`, `cardpurchase`, `cardpayment`. Income/egress use CUENTA (cash/bank; egress also allows a card via cardpurchase explicitly), CATEGORIA of matching classification and METODO from configuration. Transfers use distinct cash/bank CUENTA and DESTINO, optionally COMISION with Gasto CATEGORIA. Card purchases use card CUENTA, Gasto CATEGORIA and optional CUOTAS 1..120 plus PRIMER_VENCIMIENTO (default purchase date); monthly due dates clamp to month length and split cents exactly. Card payments use bank/cash CUENTA and card DESTINO. They debit cash and reduce debt, with no second expense, allocate FIFO against card installments; unscheduled initial debt remainder is allowed. Amount <= card debt. `pay` uses bank/cash or card for ordinary commitments; a card installment must use bank/cash and posts a card payment. Optional FACTURA/DOCUMENTO/REFERENCIA are plain text identifiers, DOCUMENTO is not binary. COMPROBANTE_URL accepts only Google Drive HTTPS file `/file/d/ID/view`, `/preview` or `/open?id=ID` URLs, <=300 characters.

## Schemas

All header names are uppercase; physical sheet names below are case-sensitive. Every entity row includes `ID USERNAME OP_ID UPDATED_AT`. IDs generated server-side on creation. Versions are append-only, same logical ID on edit; OP_ID and timestamps are server controlled. Row input accepts only business columns plus ID/UPDATED_AT. Required creation fields are marked **bold**. Optional text defaults empty, optional amounts zero, optional references empty. No financial/catalog seeds.

- **Cuentas**: **NOMBRE TIPO**, BANCO TITULAR IDENTIFICADOR SALDO_INICIAL DEUDA_INICIAL LIMITE_CREDITO FECHA_APERTURA DIA_CORTE DIA_PAGO PAGO_MINIMO PAGO_TOTAL_ESTADO ESTADO OBSERVACIONES MONEDA FECHA_CORTE FECHA_MAXIMA_PAGO. MONEDA is optional input, defaults to USD when omitted, and is always stored/returned as `USD` on created/edited account versions. If supplied on create or edit it must be exactly `USD`; no empty value, other currency, currency conversion or exchange-rate service is supported. Currency cannot be changed from USD. The last three physical business columns are MONEDA, FECHA_CORTE, FECHA_MAXIMA_PAGO. Both concrete statement dates are optional card-only real ISO dates; FECHA_MAXIMA_PAGO must be >=FECHA_CORTE when both are present. Existing DIA_CORTE/DIA_PAGO remain recurring forecast days, not proof that current debt is overdue. Statement fields are saved as append-only audited account versions, with the same ID/OP_ID/UPDATED_AT and optimistic edit rules as other account fields; changing statement metadata creates no ledger payment or adjustment. Types `Ahorros`, `Corriente`, `Efectivo`, `Tarjeta de crédito`, `Otra`; ESTADO `Activa` (default)/`Inactiva`. Credit identification last four digits only; bank identification <=100 chars; cash/other no identification. Credit debt <= limit; bank opening >=0. Credit-only fields forbidden on noncredit accounts. Opening balances and account type are locked once referenced by a confirmed ledger row.
- **Beneficiarios**: **NOMBRE TIPO**, IDENTIFICACION TELEFONO EMAIL BANCO_DESTINO CUENTA_DESTINO CONCEPTO VALOR FRECUENCIA DIA_VENCIMIENTO ESTADO OBSERVACIONES. TIPO `Persona`/`Empresa`/`Entidad financiera`; ESTADO Activo/Inactivo (default Activo); no default beneficiaries.
- **Categorias**: **NOMBRE TIPO**, ESTADO. TIPO Ingreso/Gasto; ESTADO Activa/Inactiva (default Activa).
- **Obligaciones**: **TITULO MONTO FRECUENCIA INICIO**, BENEFICIARIO CATEGORIA FIN DIA ESTADO OBSERVACIONES. FRECUENCIA `Semanal`, `Quincenal`, `Mensual`, `Trimestral`, `Semestral`, `Anual`, `Pago único`. ESTADO Activa/Suspendida/Finalizada (default Activa). DIA optional 1..31, month-based dates clamp; INICIO anchors weekly 7-day and quincenal 15-day intervals, and month-based frequency phase. Saving an active recurring definition generates only current/future occurrences within HOY..today+90 days, never invents historical unpaid debt, and never rewrites issued commitments. Pago único explicitly authorizes its single INICIO occurrence even when past. References, if supplied, must be active. No automatic payments.
- **Cuotas**: **TITULO MONTO FECHA_VENCIMIENTO**, DEFINICION FECHA_PROGRAMADA CLAVE_PERIODO BENEFICIARIO CATEGORIA TARJETA ESTADO OBSERVACIONES. ESTADO Pendiente/Anulado; generated fields DEFINICION FECHA_PROGRAMADA CLAVE_PERIODO TARJETA are server controlled and immutable. Manual row cannot set those fields. Generated card installments (nonempty TARJETA) have immutable MONTO after purchase: supplying the unchanged amount is allowed, but increases/decreases return Spanish status 409 before any writes. Title, actual due date and notes remain editable with optimistic UPDATED_AT, without changing original planned keys, allocations or ledger debt. Debt/fee changes require a separately audited new purchase or reconcile, not a silent installment-amount edit. Non-card manual/recurring commitments remain variable, with edited amount >= active allocated payments. Changing due date preserves planned date/key. Issued installments remain when recurrence changes/suspends/finalizes. All planned keys including annulled rows prevent regeneration.
- **Movimientos**: FECHA TIPO DESCRIPCION MONTO CUENTA DESTINO CATEGORIA BENEFICIARIO METODO ASIENTOS ESTADO COMPROBANTE_URL REFERENCIA MOTIVO OBSERVADO DIFERENCIA. TIPO Ingreso/Gasto/Transferencia/Compra tarjeta/Pago tarjeta/Ajuste, ESTADO Activo/Anulado. ASIENTOS is JSON array `{CUENTA,CENTAVOS}`: positive cash adds balance, positive card adds debt. Transfer is one canonical row with two postings, fee a separate Gasto row in same operation. MONTO and DIFERENCIA are dollars; signed DIFERENCIA for reconciliation, MONTO absolute delta. All rows server generated.
- **Transferencias**: MOVIMIENTO ORIGEN DESTINO MONTO COMISION ESTADO.
- **Pagos**: CUOTA MOVIMIENTO MONTO FECHA REFERENCIA FACTURA DOCUMENTO ESTADO. Each is an allocation, not another ledger movement. Paid is sum of active allocations to quota. ESTADO Activo/Anulado.
- **Configuracion**: CLAVE VALOR. VALOR JSON encoded; initial system rows have blank USERNAME/OP_ID and only USD, actual spreadsheet timezone, alert 7, overdraft false, future email channel empty, and four methods: Efectivo, Transferencia bancaria, Tarjeta de crédito, Cheque. User overrides are versioned.
- **Auditoria**: ENTIDAD ENTIDAD_ID ANTES DESPUES MOTIVO. Before/after serialized JSON, immutable, one per changed entity plus uploads. Audits carry operation and actor metadata.
- **Operaciones**: ID USERNAME REQUEST_ID HASH ACTION ESTADO MANIFEST RESULTADO ERROR CREATED_AT UPDATED_AT OP_ID. Append-only journal states PREPARADA/CONFIRMADA/PENDIENTE_CONCILIACION/DESCARTADA. ID is operation UUID. MANIFEST bounded JSON <=45,000 chars of `{sheet,id,hash}` (hash includes OP_ID and timestamp). RESULTADO is serialized stable retry result, with compact `{$sheet,$id}` references to original committed versions (expanded in API responses). OP_ID blank for journal markers, resolution operation ID for staged discard marker.

OperacionDetalle is not required: the bounded manifest is used. Every table's precise physical column order is exported as `PERSONAL_SCHEMAS` in Code.gs and in backup.schemas.

## Bootstrap Types

`{cuentas,beneficiarios,categorias,recurrentes,obligaciones,movimientos,transferencias,pagos,operacionesPendientes,configuracion,hoy}`. All lists are latest confirmed versions owned by the user, including inactive/annulled history summaries; all money values are numbers. `recurrentes` comes from Obligaciones, `obligaciones` from Cuotas. Accounts add `SALDO_ACTUAL` (cash only, null for credit), `DEUDA_ACTUAL` and `CREDITO_DISPONIBLE` (credit only, null otherwise). Never include card debt as cash. Cuotas add numeric `PAGADO PENDIENTE`, `ESTADO_ACTUAL` Anulado/Pagado/Pago parcial/Pendiente, booleans `VENCIDO PROXIMO`. Ledger includes full OP timestamp UPDATED_AT. `configuracion` includes `MONEDA TIMEZONE DIAS_ALERTA PERMITIR_SOBREGIRO METODOS CANAL_EMAIL UPLOAD_ENABLED HOY`; `hoy` is timezone-formatted actual spreadsheet today. Pending operations include ID, REQUEST_ID, ACTION, ESTADO, CREATED_AT, ERROR, not user secrets.

Accounts also expose derived `SALDO_ESTADO_PENDIENTE` (number or null) and booleans `ESTADO_CUENTA_VENCIDO ESTADO_CUENTA_PROXIMO`. Only a credit card with positive PAGO_TOTAL_ESTADO and both concrete statement dates declares a calculable statement. In integer cents: `pending = min(currentDebt, max(0, statementTotal - sum(active confirmed Movimientos with TIPO="Pago tarjeta", DESTINO=thisCard.ID, FECHA>=FECHA_CORTE)))`. The cut-date boundary is **inclusive**: payments on the closing date count; earlier payments do not. Later payments, including after the due date, count; no extra upper-date cutoff is applied. Use the canonical card-payment movement once, not its possibly multiple FIFO Pagos allocation rows. Purchases after the cut increase current debt but do not increase the user-declared statement total. Voiding a payment removes it from the sum and restores debt/pending under normal financial reversal validation. A new reconciliation changes current debt through its own audited adjustment, not the declared statement total or recorded payments.

Declared positive pending is overdue only when FECHA_MAXIMA_PAGO<HOY, and upcoming when HOY<=FECHA_MAXIMA_PAGO<=HOY+DIAS_ALERTA (the due date itself is upcoming, not overdue). A declared fully paid statement has pending 0 and both alerts false. Without positive statement total and both dates, pending is null and both alerts are false, even with initial debt or recurring payment days. Non-credit accounts also have null/false/false. These are bootstrap-only calculations, never stored running balances and never a second expense; they do not invent bank statement data. Owner supplies actual statement metadata.

## Setup, Integrity and Limits

Owner runs `setup.inspect()` before `setup.run()`; the editor entry points are `inspectPersonalStructure()` (logs inspection JSON) and `setupPersonalSpreadsheet()`. Inspection returns every actual tab with headers and compatibility and every target (including missing tabs). Setup preflights ALL targets before any write: incompatible, reordered, unknown or missing required headers fail with zero writes. Known missing optional headers append at the end, existing cells/tabs (including Hoja1) are never reset/deleted. Empty named target is initialized. Only system preferences are seeded. Setup does not seed identities, banks, balances, beneficiaries or categories. Read bootstrap requires setup first and makes no writes.

Protocol/schema version remains 1: this personal project has not been deployed and no live financial versions exist. Before the first financial write, install this exact updated source and run inspect/setup; an initialized compatible Cuentas header missing MONEDA and/or the two concrete statement dates receives only the missing appended optional headers. Existing row cells are preserved, not backfilled or reinterpreted as trusted financial seeds. Repeating setup with the same updated schema is idempotent. Do not mix source/schema revisions after financial operations begin: adding a header changes the complete row objects and therefore the ID/hash manifest verification/retry assumptions of older versions. This is a pre-deployment schema amendment, not an automatic migration of an already financed deployment; no compatibility/re-hashing/replay path is provided. Bootstrap and raw backup include stored account currency/statement metadata, with no fabricated opening/current balances or bank statement values.

Append versions, audit and allocation rows, flush, read back and verify each expected ID/hash, then append ONE CONFIRMADA marker and flush. Only versions whose operation has a CONFIRMADA marker are visible; blank OP_ID accepted only for system preferences. Exceptions yield failure and pending status, never success. A confirmed marker with an uncertain response can be retrieved by identical retry. This is a visibility/commit protocol, **not Sheets ACID**; owner must not manually alter financial rows or bypass the lock. Request IDs are namespace-global to prevent user substitution. Financial validation considers the entire proposed operation, including voids: no cash overdraft unless configured, no negative card debt or debt above credit limit. No stored running balances.

Generation: recurring candidates are limited to the inclusive HOY..until window, with default until=HOY+90 days and maximum until=HOY+366 days. The backend fast-forwards mathematically from INICIO; there is no recurrence-age limit or 36-month traversal limit. Weekly and quincenal remain anchored to the original 7/15-day sequence. Monthly/trimestral/semestral/anual remain anchored to their original month phase and DIA (or original start day), with month-end/leap-year clamping, not to the last generated clamped date. A recurring definition whose FIN is past creates no new commitments. A past Pago único is the explicit exception: it creates its single planned INICIO occurrence if <=until and within FIN, never a ledger payment. All existing past/current/future Cuotas remain untouched, including overdue, paid, edited and annulled rows. Every issued planned key prevents regeneration, even if annulled or due-date-overridden. Editing INICIO does not rewrite history; future candidates with existing identical definition+planned-date keys are skipped. An explicitly changed anchor that yields genuinely different future dates can add those dates without silently cancelling previously issued schedules.

Generation is limited to 100 NEW occurrences across all definitions in one operation; already issued keys do not count. Two unissued weekly schedules over a 366-day inclusive window can produce 53+53=106 candidates and therefore fail. Use definitionId to generate each schedule separately or shorten until. Limit failures return `{success:false,status:400,message}` in Spanish and perform zero Sheets/Drive writes, create no prepared journal entry, and return no partial generated list; there is no automatic pagination or silent truncation. Saving a definition remains all-or-nothing with its automatic 90-day generation. Suspended/finalized definitions are skipped; one failing active definition aborts global generate. Historical INICIO itself is not a failure and requires no user start-date adjustment. Historical unissued recurring debt is never inferred automatically: explicitly save manual Cuotas if needed. Normal calendar dates within 1900..9999 remain valid for standalone transactions/commitments; computed card due dates must also stay in that range. Card scheduling is independent of recurrence generation and supports up to 120 monthly installments, with at least one cent per installment. Manifest/result size limits still bound each operation; oversized changes fail before preparation. Void refuses dependencies paid by other active operations. All histories are read under lock, so growing sheets are subject to normal GAS execution, memory and Sheets/Drive quotas; production latency and quota behavior still require deployment testing. No physical deletion, destructive restore, banking APIs, emails or exchange-rate services.

Uploads: owner optionally sets DRIVE_FOLDER_ID and grants Drive scope. Folder must not have public/link sharing. Files JPG/PNG/PDF validated by MIME, extension, decoded magic, strict base64 and <=3 MiB. Upload is private, never setSharing; bytes never written to Sheets. A Drive failure can leave a private orphan file, recorded operation stays pending and is not replayed. Receipt URL permissions remain Drive permissions; no automatic public sharing or Google viewer. Without folder, UPLOAD_ENABLED=false and frontend can enter a validated external Drive URL. Owner deploys execute-as-owner with API secret behind trusted proxy; configure integration/deployment separately.

Upload payload uses `filename`, not `name`. UPLOAD_ENABLED indicates that DRIVE_FOLDER_ID is set, not that its permissions/access have been verified. Missing folder configuration returns 503; non-private sharing returns 400; inaccessible/missing folders or Drive access errors during preflight return a generic 500 message without exposing Drive exception details. These preflight failures create no file, audit or journal row. Frontend may offer external Drive URL entry after such failures. A failure after file creation instead returns 503 with a reserved pending operation; resolve explicitly rather than retry with a fresh UUID.

External COMPROBANTE_URL must use the exact `https://drive.google.com` host, a file ID of at least 10 characters from `[A-Za-z0-9_-]`, and either `/file/d/ID/view`, `/file/d/ID/preview` or `/open?id=ID`. View/preview paths may include a query introduced by `?`; open links may append query parameters introduced by `&`. Additional query text permits only `[A-Za-z0-9_=%&.~+\-]`, supporting normal `usp=sharing`, `usp=drive_link` and `resourcekey` links. The complete input URL, including query order, percent encoding and resource keys, is preserved verbatim in the movement and audit; parameters are not stripped or canonicalized because resource keys can be required for access. The 300-character limit includes the query. Userinfo, ports, alternate/spoofed hosts, fragments, whitespace (including a trailing newline), folder links and non-HTTPS schemes are rejected. This permits linking a Drive file, not fetching it or changing its permissions. Backend-generated upload URLs remain the plain `/file/d/ID/view` form.

Base64 must use the standard alphabet, length divisible by four, zero to two padding characters only at the end, and canonical unused padding bits. Validation uses a linear character scan and decoded-byte re-encoding, not a repeating grouped regex. Encoded length is limited to 4,194,304 characters; decoded size is limited to 3,145,728 bytes (exactly 3 MiB is accepted). No whitespace, data-URL prefix or URL-safe alphabet is accepted. Filenames are limited to 120 characters. Malformed or oversized input is rejected with Spanish status 400 before any file, audit or operation journal entry is created. Sheets persist only operation IDs/hashes, bounded manifest, receipt URL/file ID and audit metadata, never receipt bytes or Base64 contents.
