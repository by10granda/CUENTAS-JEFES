# Mocked Browser Tests

Install Chromium with `npx playwright install chromium`, then run `npm run test:e2e`. The config starts Vite at http://localhost:5173 or reuses an existing development server there. No API process is required because all API responses are intercepted. If you use a custom browser install directory, set `PLAYWRIGHT_BROWSERS_PATH` to that directory when installing and running tests.

These tests exercise the real frontend with intercepted `/api/index` responses using the documented API envelope. Public config is mocked as `{authMode: 'password', configured: true/false}` without credentials; sessions use `{username, name}`. They are not live password-authentication, backend, Sheets, or Drive integration tests and need no real credentials. Unexpected API actions and external requests fail the tests.

Google Fonts CSS is intercepted with an empty stylesheet so tests use local fallback fonts without network access. Login uses test-only shared username/password fixtures and intercepted responses; no Google login scripts or Google Cloud configuration are needed. Passwords and secrets for the real application belong only in private server variables, never Sheets, frontend configuration, or chat.

The default bootstrap contains only approved catalogs, with empty accounts and movements. Registration works directly by choosing jefe and movement data, without accounts or opening balances; no account creation, selection, filter or display UI exists. Historical account sheets/fields remain compatible, not replaced by fake default accounts. Income, expense, and payment amounts exist only in opt-in synthetic fixtures under this directory and are never written to production services.

Both desktop and mobile Chromium run 13 scenarios: setup warning, password login, empty dashboard, accountless movement/identical retry after reload, linked-payment accounting, actual XLSX/PDF downloads, optional validated Drive URLs with no uploads, positive accountless transfers, historical metadata/receipt preservation on edit/retry, deliberate type/jefe changes clearing account metadata, investment filters, unsafe historical receipt suppression, and same-jefe linked payments without account inheritance. Login checks retain failed credentials, clear the password on success, and ensure it is not stored in browser storage; drafts are keyed by username. Screenshots and traces are retained on failure. Downloads and runner artifacts are generated under `e2e/test-results/`.

Total invertido sums full `TOTAL` of live independent Gasto, Compra and Pago, including pending/partially paid obligations, excluding linked-payment duplicates and void records. It follows shared filters and jefe selections, independently of accounts; it is not actual cash disbursed. Reimbursements do not reduce it, and loans, advances, income, transfers and withdrawals do not add it. Counts include all selected live movements, not only investment-bearing records. Pending amounts consider all linked payments, including outside the selected period. Accountless transfers are positive and paid but do not redistribute money. Legacy account balances cover accounted records only, not the complete dataset; `CUENTAS` writes return 403 in the backend, not a browser-mock guarantee.

Receipts are optional URL-only fields, with a 300-character limit, not a file-size limit. Empty is allowed; edit omission preserves the URL and explicit blank clears it. The allowlist is HTTPS `drive.google.com/file/d/ID/view` or `/preview` with the accepted shared query characters, or `/open?id=ID` with optional shared query parameters; see the exact regex in `server/CONTRACT.md`. Unsafe historical values are not linked in tables, detail or reports. No file input or upload flow exists; the removed action returns 404 in Node/Apps Script. A URL cannot attest file privacy, existence, safety or permissions; private files require separate Google viewer access. No Drive OAuth or `DRIVE_FOLDER_ID` is required. Node's legacy 7 MiB JSON request limit and host limits/Apps Script quotas still apply, not as file-upload capacity.

Verification: 26 browser tests passed (13 scenarios on desktop and mobile), 43 unit/HTTP tests passed, and the production build passed. Repository: https://github.com/by10granda/CUENTAS-JEFES, branch `main`. Connected reads were checked on the previous deployment. Live accountless writes and the new receipt policy require updating and republishing the remote Apps Script; Google receipt-viewer access is separate from application authentication.

The public link intentionally admits anyone with the shared credentials the owner will configure later. Login environment variables are unchanged; no new Google credentials are needed. Audit records use that shared username, not per-person attribution, and historical audit emails are preserved. Before connected testing, replace remote Apps Script with the latest complete `apps-script/Code.gs` and current Sheets-only manifest, then republish **Nueva version** at the same `/exec` URL. An email-to-username-only patch is insufficient: the new normalizer allowing optional accounts is mandatory, along with same-jefe links, read-only accounts, accountless transfers and URL-only receipts with uploads removed. `ID requerido CUENTAS` indicates the old remote normalizer; update/redeploy it, never create a fake account to bypass it. Preserve every table and historical row. This upgrade introduces no new schema/header changes or setup reset; already compatible sheets need no setup rerun, and the existing setup handles optional-column compatibility if needed. Public `/exec` GET always denies access by design.

Browser mocks do not prove resistance to brute force. No distributed lockout or application-level password-attempt limit is implemented; the public login endpoint permits repeated attempts. Configure and verify Vercel firewall/rate limiting for both login routes before real production, rather than treating these tests as evidence that this protection exists.
